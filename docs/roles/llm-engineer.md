# LLM Engineer

An LLM engineer builds and operates applications that connect language models with retrieval, tools and evaluation.

**Classification:** Overlapping employer title · **Foundations:** Backend development, Information retrieval · **Focus:** language-model applications

**Related titles:** generative AI engineer, NLP engineer, AI/ML engineer

<span id="how-this-role-is-changing"></span>
<span id="what-the-work-looks-like"></span>

## What you do

Ingest documents with metadata and permissions, select useful context, connect models to approved tools, and measure quality, latency, cost and failures. Reliability and context pipelines add specific concerns to backend work. The title overlaps AI engineering and can mean applications, model adaptation, inference or research; it does not always involve training a foundation model.

<span id="skills-to-develop"></span>

## Skills

- Python or TypeScript/Node, HTTP APIs, Git and automated tests.
- Data processing, SQL, chunking, embeddings, ranking and retrieval.
- Structured outputs, prompt/context design and failure handling.
- Versioned evaluations that distinguish improvements from regressions.
- Deployment, monitoring, permissions and operating-cost measurement.

<span id="entry-routes-and-search-terms"></span>

## Example requirements

**seRevel — LLM Engineer:** production retrieval, agent tools, regression tests, data permissions and operating cost. It asks for TypeScript/Node, shipped production work and useful regression evaluations.

**REI Systems — AI/ML & LLM Engineer:** a **mid-senior** example spanning traditional ML, enterprise search and generative services, with Python, SQL, deployment, monitoring and version tracking.

Neither establishes routine entry-level access. Backend/full-stack work, NLP, data engineering and ML are related routes to investigate; students can practice a smaller lifecycle in projects or internships.

<span id="a-portfolio-project-that-shows-the-work"></span>

## One project

**Source-citing course handbook assistant.** Use public course documents or a synthetic collection.

1. Hold out **40 questions**, including **10 unanswerable** cases, and compare keyword search with retrieval.
2. Define correctness, citation support and abstention rubrics before testing.
3. Publish results, failures, model/configuration versions, median latency and measured cost with the test setup.
4. Demonstrate that an unauthorized test user cannot retrieve restricted documents.

Include reproducible setup, a short demo, and one failed change that informed your next decision.
